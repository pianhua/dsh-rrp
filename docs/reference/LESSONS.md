# 旧项目复盘（LESSONS.md）

> 对象：`D:\projects\dsh-custom-agent`（上一代实现）  
> 目的：**避免重演同样的膨胀路径**；并明确哪些资产值得继承。

## 1. 事实规模

| 维度 | 规模 |
| :--- | :--- |

## 2. 膨胀的根因（按严重度）

### ① 在「RP 插件」外壳下造了一个平行平台（最主要）

旧项目的目录体量重头**不是玩法，而是平台**：

| 目录 | 约行数 | 本质 |
| :--- | ---: | :--- |
| `src/change/` | 6800+ | 状态机 + 账本 + CAS + 仲裁（域与基建混杂） |
| `src/web/` | 5700+ | **自建 HTTP / API / SSE** |
| `src/ui/` | 5700+ | **自建整站游玩前端** |
| `src/runtime/` | 5700+ | **自研回合编排 OS** |
| `src/devconsole/` | 3900+ | **第二套调试前端** |
| `src/background/` | 1700+ | **自研任务队列 / 死信 / 恢复** |
| `src/persistence/` | 1600+ | **自研通用 SQLite 框架** |

结论：它长成了「**迷你应用平台 + 少量 RP 域**」，而宿主本来就有这些能力。

### ② 过度防御性编程

为「玩家可能改状态」发明了：CAS 乐观锁、永久仲裁保护盾、解绑通道、拒写保护、冲突校验……
→ 而真实需求只是 **D6 的自然时序矫正**（覆盖 + 下一轮消费）。

### ③ 双轨兼容只增不减

- `codex` **和** `lorebook` 两套目录/API 并存
- 原生 `cards/` **和** `character-card`（PNG 路径）并存
- `storyId` 标准名 **和** 代码里残留的 `chatId`
- `Author/Chronicler` 标准名 **和** 口述的 `Agent 1/2`

每代实现都「加一层兼容」，几乎不删除 → 代码与心智模型双膨胀。

### ④ 测试锁死了平台

3.3 万行测试大量在验证自研平台细节（持久化样板、恢复矩阵、Web 命令边界、runtime 细节）。
→ 想瘦身时，569 全绿反而成了阻力：**绿的是旧轮子**。

### ⑤ 文档退化成阶段流水账

`ACTIVE_TASK.md` / `STATUS.md` 被写成万字阶段战报，导致：
- 新人（含新 AI）无法从入口建立心智模型
- 真实设计意图被埋在「切片 20.x 已完成」的历史记录里

## 3. 该继承的资产（语义，不是文件）

| 资产 | 为什么值得留 | 新形态 |
| :--- | :--- | :--- |
| **双智体权能分立** | 作者不记账、记账不写正文，是正确的架构直觉 | 重写为 DSH Agent |
| **玩家矫正的产品承诺** | 「AI 会记错，玩家必须能当场改」是核心体验 | 简化为无锁自然时序（D6） |
| **状态承载角色演进** | 防止人设僵化导致剧情漂移与出戏 | 动态结构（D5） |

| **非线性世界线哲学** | 拒绝气泡翻页、历史永不丢 | 映射原生 fork（D9） |
| **大局观摘要** | 长线叙事防偏航 | 独立摘要智体（D11） |
| **Author 提示词中的防代打约束** | 治理酒馆最恶心的体验问题 | 保留为 Author 铁律 |

## 5. 给后续实现者的警告

1. **不要「先去旧仓找对应文件抄一份」** —— 那是把平台代码搬进新仓的最快路径。
2. 若确实需要旧实现细节（例如提示词措辞），**只取语义**，并在 `DECISIONS.md` / `GLOSSARY.md` 约束下重写。
3. 每个新模块落地前，先问三遍：**宿主是不是已经有了？**（见 [`HOST_ALIGNMENT.md`](../HOST_ALIGNMENT.md)）
4. **代码量本身是警报器**：一个新功能如果带来数千行，通常意味着在造平台。
5. **文档不许写成战报**：本层只记「为什么」，不记「第几轮做了什么」。
