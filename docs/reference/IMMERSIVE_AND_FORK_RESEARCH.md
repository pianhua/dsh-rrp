## 一、沉浸模式（story-view）现状

### 1.1 已实现

**代码**：`src/client/story-view.tsx`（147 行，已完成）

**形态**：
```
注册位置：conversation.view slot（与 DSH 原生 Chat 并列）
展示方式：纯增量 tab，不替换宿主的 Chat 渲染器
内容提取：订阅 chat target 快照，只取 user/assistant 文本
排版风格：居中 720px 衬线栏，17px 字号，2.05 行高，两端对齐
玩家输入：斜体 + 左侧竖线（视觉区分动作与正文）
自动滚动：新消息到达时滚到底部
```

### 1.2 关键判断：它不是"必要的"，是"体验增益"

| 维度 | 原生 Chat | 沉浸模式 |
|:---|:---|:---|
| 功能可用性 | ✅ 完全可用 | ✅ 只读展示 |
| 工具调用可见 | ✅ 显示 | ❌ 过滤掉 |
| 状态/系统消息 | ✅ 显示 | ❌ 过滤掉 |
| 阅读体验 | 代码助手风格 | 文学小说排版 |
| 可交互性 | 完整（编辑、重试等） | 只读 |

**结论**：
沉浸模式是**阅读层的糖**，不是功能必需。
它的价值在于：把"带工具调用的技术转录"变成"干净的小说正文"。
代价是：只读，无法在沉浸视图里做编辑/重试等操作。

### 1.3 当前是否够用

**已具备**：
- ✅ 文学排版（衬线、行高、两端对齐）
- ✅ 噪声过滤（跳过 tool/system/context 节点）
- ✅ 玩家输入视觉区分
- ✅ 自动滚动

**缺失**：
- ❌ 无分支/撤回入口
- ❌ 无历史节点标记（无法看到"这里分叉了"）
- ❌ 无正在生成时的流式反馈（依赖宿主）
- ❌ 无章节/回合导航（长文难定位）

## 二、分支/撤回现状

### 2.1 关键发现：DSH 宿主已原生支持 fork

**宿主能力**（`dsh-api-session-controller`）：
```typescript
sessions.fork({
  sessionId: SessionId,
  atSeq?: number,        // 可选：从哪个事件序列分叉
  increaseTitle?: boolean // 子会话标题是否递增
}): Promise<SessionId>
```

**底层保证**（`dsh-session` README）：
> `fork()` creates a child session from a stable prefix of a live one.
> 要求：前缀必须结束在 turn 之外（不能在 turn 中间切）
> 子会话带 lineage metadata，`inheritedEventCount` 记录切点

**UI 中也有**：
- `dsh-client-ui-chat` 的 client.js 中存在 `fork` / `forkAt` / `forks` 标识
- 说明宿主 Chat UI 已经有分支入口（可能是消息右键菜单）

### 2.2 我们的插件做了什么

**结论：几乎什么都没做。**

查看 `context-types.ts`，我们的 `RrpSessionsService` 只声明了：
```typescript
create(options): Promise<string>
open(id): void
binding(id): RrpSessionBindingFace | undefined
```
**没有声明 fork。**

**但这是设计上的正确选择**：
- 遵循"不自建平行世界"铁律
- 分支是 DSH 原生能力，不该由插件重复实现
- `AGENTS.md` 明确写："世界线分支完全映射 DSH 原生会话分叉"

### 2.3 为什么页面上看不到？

**三个可能原因**：

**原因 A：入口在原生 Chat 里，不在沉浸视图里**
- 我们的 `story-view` 是纯只读展示
- 没有提供任何交互控件
- 分支入口应该在原生 Chat 的消息操作里

**原因 B：需要满足条件才出现**
- fork 要求"切点必须在 turn 之外"
- 如果消息处于生成中，可能隐藏入口
- 可能需要先选中某条消息

**原因 C：还没被触发/发现**
- 入口可能是 hover 显示、右键菜单等隐式交互
- 或者仅在特定视图模式下出现

## 三、撤回（rewind）现状

### 3.1 DSH 的机制

DSH **没有传统的"撤回"**，而是用 fork 实现等价效果：
```
传统撤回：删掉最后 N 条消息，从那里重新开始
DSH fork：从第 N 条之前分叉出新会话，原会话保留
```

**为什么这样设计**：
- 不可变日志（append-only），历史永不丢失
- 分支可追溯，不会"回退后忘了之前写过什么"
- 符合我们 DESIGN.md 的"告别翻页伪分支与幽灵状态"

### 3.2 我们的投影如何配合

这是我们的优势所在：
```
fork 时：子会话继承父会话到切点的所有事件
投影折叠：WorldState/Summary/Settings/Sediment 从事件流重放
结果：子会话的世界状态精确等于切点的状态，无幽灵数据
```

**已在 P0 验收中验证**（第 5 项：Fork 继承与分流）。

## 四、结论与建议

### 4.1 直接回答你的两个问题

**Q1：沉浸模式的必要性？**
> 不是功能必需，是阅读体验增益。它把技术转录变成小说排版。
> 当前实现已达"可用且优雅"，但缺交互能力（分支、导航）。

**Q2：分支/撤回为何看不到？**
> 因为分支是 DSH 宿主能力，入口在原生 Chat UI 里，不在我们的沉浸视图里。
> 我们的插件"正确地"没有重复实现它。
> 但这也意味着：**如果你只在沉浸视图里玩，就看不到分支入口。**

### 4.2 待确认事项（需要你实测）

**请测试**：
1. 在**原生 Chat 视图**里，悬停某条消息，是否出现分支/操作按钮？
2. 右键消息是否有"分支"或"从这里重新生成"？
3. 如果原生 Chat 有入口，切换到沉浸视图后是否消失？

### 4.3 可选增强方向（待你决策）

| 方向 | 说明 | 成本 |
|:---|:---|:---|
| **A. 沉浸视图加分支按钮** | 在每条 assistant 消息旁加"从这里分叉" | 低（调宿主 fork API） |
| **B. 沉浸视图加节点标记** | 显示"此处已分叉"视觉提示 | 中（需读 lineage 信息） |
| **C. 保持现状** | 分支只在原生 Chat 用 | 零 |
| **D. 章节导航** | 长文侧边长回合/场景跳转 | 中 |

**我的建议**：先确认原生 Chat 的入口是否存在。
- 如果存在且好用 → 选 C（保持现状，零成本）
- 如果你更想在沉浸视图里操作 → 选 A（低成本，高价值）
